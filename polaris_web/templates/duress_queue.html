How duress detection works

Each IdentityToken may optionally carry a Werkzeug scrypt hash of a secondary "duress" code. During verification, the operator's terminal accepts a "Holder verification code (optional)" input. When the holder enters their duress code under coercion:

  1. R1 (constant-time): check_password_hash compares the input against the stored hash in constant time — a coercer measuring response latency cannot distinguish match from mismatch.
  2. R2 (identical observable behavior): the verification flow proceeds with whatever outcome the operator specified. The coercer-visible response page is identical to a normal verification.
  3. R3 (audit-of-record): a row appears in this table. DuressEvent is the 8th audit-of-record instance, append-only via trigger.
  4. R6 (anti-revealing): the operator-visible /verifications list does NOT join to DuressEvent. Only this page and the JSON API expose duress signals, both gated to admin/auditor role.

See DEVNOTES/ships/duress-codes.md for the full mechanism design, the OOB channel future-fields (SMS, Slack, SIEM), and the v1/v2 split.
