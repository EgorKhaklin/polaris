What the schema enforces

Ten hard constraints (C1–C10) are not policies. They are triggers, CHECK constraints, partial unique indexes, and append-only audit trails. The system cannot be operated in a way that violates them.

C1

Audit of record

Every state change of an identity token writes a TokenLifecycleEvent row. Every verification writes a VerificationEvent. Both tables are append-only at the trigger level. Twelve audit-of-record instances now span schema + filesystem (sanctum, treasury, census).

C2

Zero knowledge

Verifications at the ZERO_KNOWLEDGE disclosure level have token_id IS NULL — enforced by trigger, CHECK, and form coercion. The verification graph cannot be reconstructed from ZK events. A real Plonky2 ZK-SNARK proves membership without revealing which token.

C3

One identity per person

A partial unique index makes a second ACTIVE token for the same individual a database-level error. Concurrent writes lose the race deterministically.

C10

Identity is not money

The schema has no transactions, balances, spending patterns, or merchant codes. Adding any of those would require a constitutional amendment that the agent refuses on sight. The pomerium holds: swarm currency (denarius) and identity tokens are different ledgers.

Six more constraints round out C1-C10: C4 atomic failed-login counters (no TOCTOU race); C5 CSP forbids inline scripts (no script-src 'unsafe-inline'); C6 server-side disclosure enforcement (client cannot upgrade ZK to FULL); C7 no hardcoded cryptography (algorithm references the CryptographicAlgorithm table; rotation is a row update); C8 bounded result sets on all /api/atlas/* endpoints (no unbounded query exhaust); C9 concurrency hazards tested with real threading, not mocks. The four cards above are the highlight reel for first-time visitors; the canonical text for all ten lives in MISSION.md §"The hard constraints". Anti-coercion is the vocation all ten constraints serve — named in MISSION.md §"Vocation" above C1-C10 (v9.11).

Built on real cryptography

ML-DSA-65

NIST FIPS 204 lattice-based signatures. Post-quantum secure under the Module-LWE assumption.

Plonky2 ZK-SNARK

FRI-based, transparent setup, hash-only commitments. Proves epoch membership without revealing which token.

Merkle anchoring

SHA3-256 Merkle commitments over batched anchor sets. Per-leaf inclusion proof is logarithmic in batch size.

Multi-sig migration

M-of-N signature schemes per token. Algorithm rotation without invalidating existing tokens.

Duress codes

Constant-time comparison. Coercer-visible flow is identical to the legitimate one. DuressEvent row appears in the audit table.

Federation

Per-context trust attestations. Agency V accepts agency I for context C until date D. No transitive trust.

A cognitive substrate that watches itself

Polaris's most unusual layer is the one that monitors the rest. Nine HYDRA watchers, thirty-three autonomous Mycelium ants, six Civitas citizens, and a constitutional meta-constraint (CM) that re-evaluates the system against its own claims on every session.

  • Sanctum protocol — every MEDIUM/HIGH-risk decision gets a structured agent-operator consultation on file. 36 sessions and counting.
  • Audit-of-record discipline — twelve current instances. Nothing happens that the system can't reconstruct.
  • Bounded autonomy — LOW-risk autonomous, MEDIUM propose-and-wait, HIGH explicit-human-approval. The risk-class lattice is the agent's contract.
  • Constitutional meta-constraint (CM) — the immortal tenth head. Self-monitoring is the part of the system that survives if every other layer fails.

Deployable in production

Arc B (May 2026) closed the gap between architectural sophistication and operational reality. The complete production stack ships in the repo. 

git clone <polaris repo> && cd polaris
./scripts/polaris-generate-secrets.sh
export POLARIS_DOMAIN=polaris.example.com
./scripts/polaris-deploy.sh prod
curl -fsS https://${POLARIS_DOMAIN}/api/health | jq .

Within ~90 seconds: Caddy provisions Let's Encrypt TLS, Postgres + Redis + gunicorn come up, /api/health returns structured per-component status. The operator runbook is OPERATIONS.md; the secrets primer is SECRETS.md.
